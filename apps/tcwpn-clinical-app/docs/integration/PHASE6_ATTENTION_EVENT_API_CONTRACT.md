# ClinAnx Phase 6 — Frozen AttentionEvent API Contract

Status: **client-first contract implemented in ClinAnx; Central Backend implementation pending**.

This contract is based on the R26-DS-012 integration handbook target routes and the existing ClinAnx `AttentionEvent` domain model. It is intentionally explicit so the backend can be implemented independently without changing the mobile client.

## Authority rules

- Central Backend owns event creation, assignment, lifecycle, actor identity, timestamps, persistence and concurrency.
- ClinAnx never creates an authoritative AttentionEvent from a risk score, colour, TC-WPN output or local state.
- Notification delivery, dismissal and tap are not ACK/RESOLVE.
- All clinician event reads/mutations must be assignment-scoped by the backend.
- Actor identity comes from the authenticated clinician token, never from request JSON.
- Lifecycle timestamps are generated by the backend in UTC.

## Authentication

Every endpoint below requires:

```http
Authorization: Bearer <clinician-jwt>
Accept: application/json
Content-Type: application/json
```

Expected authorization semantics:

- `401` — missing/invalid/expired clinician session.
- `403` — authenticated clinician is not permitted to access the subject/event/action.
- `404` — event does not exist.
- `409` — lifecycle mutation conflicts with current canonical state.
- `400` / `422` — invalid request.
- `5xx` — backend/service failure.

## 2. Activity/history

All assigned events:

```http
GET /v1/attention-events
```

One assigned subject:

```http
GET /v1/attention-events?subject_id=subject-001
```

Response wrapper is the same:

```json
{"events": [...]}
```

Filtering must happen on the backend. ClinAnx does not use local filtering as an authorization boundary.

## 4. Acknowledge

```http
POST /v1/attention-events/{event_id}/acknowledge
Content-Type: application/json

{}
```

The request deliberately contains no clinician id and no timestamp.

Required server behavior:

- atomically transition `OPEN -> ACKNOWLEDGED`;
- derive `acknowledged_by` from the authenticated clinician;
- create `acknowledged_at` on the server;
- persist the mutation;
- return the full canonical event.

Response:

```json
{
  "event": {
    "id": "evt-001",
    "subject_id": "subject-001",
    "fusion_result_id": 123,
    "forecast_result_id": "fcst-001",
    "event_type": "acute_escalation_forecast",
    "severity": "high",
    "reason": "Forecast crossed versioned escalation policy",
    "forecast_horizon": 10,
    "status": "ACKNOWLEDGED",
    "created_at": "2026-09-16T12:22:00Z",
    "acknowledged_at": "2026-09-16T12:24:00Z",
    "acknowledged_by": "DR001",
    "resolved_at": null,
    "resolved_by": null,
    "policy_version": "escalation-v1"
  }
}
```

If another clinician has already changed the event, return `409`. ClinAnx will reload canonical event state rather than manufacture local success.

## 5. Resolve

```http
POST /v1/attention-events/{event_id}/resolve
Content-Type: application/json

{}
```

Required server behavior:

- atomically transition `ACKNOWLEDGED -> RESOLVED`;
- derive `resolved_by` from the authenticated clinician;
- create `resolved_at` on the server;
- persist the mutation;
- return the full canonical event.

Response wrapper:

```json
{"event": {...}}
```

The current ClinAnx repository sends an empty body. If a future UI adds a resolution note/reason, that should be introduced as an explicit versioned contract change rather than silently changing this endpoint.

## Persistence model required on backend

At minimum the backend needs persistent fields equivalent to:

```text
id
subject_id
fusion_result_id
forecast_result_id
event_type
severity
reason
forecast_horizon
status
created_at
acknowledged_at
acknowledged_by
resolved_at
resolved_by
policy_version
```

Lifecycle:

```text
OPEN -> ACKNOWLEDGED -> RESOLVED
```

The backend also needs clinician-to-subject assignments so list/detail/mutation authorization is enforced server-side.

## Client behavior already implemented

ClinAnx now expects this exact contract through `CentralBackendAttentionEventRepository`:

- OPEN polling for Phase 6 local notifications;
- clinician-scoped notification dedupe by exact event id;
- event detail fetch after authenticated notification tap;
- server-canonical ACK/RESOLVE state;
- no locally generated actor/time/state;
- no local fallback event when backend is unavailable;
- `401`, `403`, `404`, `409`, validation, server and malformed-response errors remain explicit.

Until the Central Backend implements these endpoints, production calls will fail at transport/runtime; the mobile contract itself is frozen and test-covered.
